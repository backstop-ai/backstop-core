# ADR-0009: CI/CD Pipeline — Standardized Actions, Gate, Pluggable CD

**Number:** ADR-0009
**Created:** 2026-03-18
**Status:** Accepted
**Deciders:** @bmanson
**Decisions:** D-077, D-059, D-068

---

## Context

If backstop's thesis is "if it's green, it ships," then backstop must own the pipeline that defines what "green" means and what "ships" does. The gate — the ship/no-ship decision point — is the mechanical embodiment of D-059. It cannot be left to ad-hoc CI configuration.

Backstop ships three layers of GitHub Actions:
1. **CI Actions** — always-on validation and verification
2. **Gate Action** — the ship/no-ship decision
3. **CD Actions** — pluggable deployment providers

All CI Actions import `pkg/validate/` directly (D-068). No CLI installation in CI. No version mismatch. First-class GitHub integration.

## Decision

### Layer 1: CI Actions (always-on)

These actions run on every PR and push. They are generated by `backstop init` and committed to `.github/workflows/`.

**`backstop/validate`** — the core enforcement action
- Schema validation, pack checks, AST analysis
- Baseline comparison (only new violations fail)
- Waiver resolution (active waivers suppress matching rules)
- Outputs: GitHub annotations on specific lines, check run summary

**`backstop/test`** — test suite verification
- Runs the project's test suite
- Verifies mandated test names from specs exist
- Verifies test bodies are substantive (AST analysis)
- Outputs: test results as check run, failed test annotations

**`backstop/security-scan`** — security enforcement
- ASVS code-level checks from the security pack
- Dependency vulnerability scanning (supply chain)
- License compliance checking
- Outputs: security findings as annotations, advisory comments on PRs

**`backstop/ledger-verify`** — provenance verification (when workflow.ledger is enabled)
- Hash chain integrity — walk backwards, recompute hashes, confirm unbroken chain
- Completeness — all spec claims have corresponding test passes in the ledger
- Continuity — no gaps in sequence numbers
- Outputs: ledger status in check run summary

### Layer 2: Gate Action (the decision point)

**`backstop/gate`** — aggregates all CI results and decides ship/no-ship

The gate action is the thesis in action. It:
1. Waits for all CI actions to complete
2. Reads their check run results
3. Applies the project's `review_policy` from backstop.yml
4. If `backstop-only`: auto-merges when all checks pass (configurable)
5. If `human-required`: marks PR as ready for review when all checks pass

```yaml
# .github/workflows/backstop-gate.yml
name: Backstop Gate
on:
  check_suite:
    types: [completed]

jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: backstop/gate@v1
        with:
          auto_merge: true           # merge when green (configurable)
          required_checks:
            - backstop/validate
            - backstop/test
            - backstop/security-scan
            - backstop/ledger-verify  # only if workflow.ledger is true
```

The gate action is the **merge authority** — not human approvers. This is D-059 made mechanical.

### Layer 3: CD Actions (pluggable, opt-in)

CD providers are added via `backstop cd add <provider>`. Each provider is a recipe with a standardized interface:

```bash
$ backstop cd add vercel
# Prompts for credentials → stores as GitHub secrets
# Generates .github/workflows/backstop-deploy-vercel.yml
# Gate action triggers deployment when ship decision is positive
```

Available providers (each is a separate action):
- `backstop/deploy-vercel`
- `backstop/deploy-fly-io`
- `backstop/deploy-aws-ecs`
- `backstop/deploy-cloudflare-workers`
- `backstop/deploy-kubernetes`

Provider interface contract:
```yaml
inputs:
  trigger: "gate-passed"      # only deploy when gate says ship
  environment: "production"   # or staging, preview
  # provider-specific inputs (credentials come from secrets)
```

New providers are added as recipes in the standard library. The interface is standardized; the implementation is provider-specific.

### Pipeline composition

`backstop init` generates the complete pipeline:

```
.github/workflows/
  backstop-ci.yml           ← validate + test + security-scan + ledger-verify
  backstop-gate.yml         ← aggregation + ship/no-ship decision
  backstop-deploy.yml       ← CD provider (if configured)
```

The pipeline is committed to the repo, not generated on the fly. Teams can customize the workflows — backstop generates the starting point, not a locked-down black box.

### Rich CI output

Because Actions import `pkg/validate/` directly, they produce GitHub-native output:

- **Line-level annotations** — violations appear inline on the PR diff, exactly where the issue is
- **Check run summaries** — aggregated pass/fail with violation counts and categories
- **PR comments** — detailed security findings, baseline progress, waiver expirations approaching
- **Status checks** — standard GitHub required status checks that block merge

This is richer than anything a CLI-in-CI approach could produce. The Actions ARE the CI, not a wrapper around a CLI.

## Consequences

### What this enables
- **"If it's green, it ships" is automated.** The gate action makes the merge decision mechanically. No human bottleneck.
- **Rich developer feedback.** Violations appear inline on the PR diff, not buried in CI logs.
- **Pluggable deployment.** Add a CD provider with one command. Standard interface, provider-specific implementation.
- **Pipeline as code.** The entire CI/CD pipeline is committed, versioned, and customizable.

### What this requires
- **GitHub Actions as the CI platform.** Backstop's first-class CI integration targets GitHub. Other platforms (GitLab CI, CircleCI) are future work.
- **Action versioning.** Actions follow semver. Breaking changes require major version bumps.
- **Provider recipe maintenance.** Each CD provider needs an action that stays current with the provider's API.

### What this does NOT mean
- **Backstop replaces CI.** Backstop's actions compose with existing CI workflows. Teams keep their existing test runners, build steps, and custom actions.
- **The pipeline is locked down.** Generated workflows are starting points. Teams can customize, add steps, change triggers.
- **CD is required.** CI and gate ship by default. CD is opt-in via `backstop cd add`.

## Alternatives Considered

| Approach | Why Rejected |
|----------|-------------|
| CLI in CI (`run: backstop validate`) | Requires installing the binary, managing versions, parsing CLI output. Actions importing the library directly is simpler and produces richer output. |
| Backstop-specific CI platform | Over-scoped. GitHub Actions is where the users are. Meet them where they are. |
| No gate action (manual merge decision) | Contradicts the thesis. "If it's green, it ships" requires a mechanical decision point. |
| CD built into the CLI | Deployment is an infrastructure concern, not a validation concern. Actions are the right abstraction for CI/CD. The CLI is for validation. |
