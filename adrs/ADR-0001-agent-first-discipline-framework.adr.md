# ADR-0001: Backstop Is an Agent-First Discipline Framework

**Number:** ADR-0001
**Created:** 2026-03-17
**Status:** Accepted
**Deciders:** @bmanson
**Decisions:** D-052, D-024
**Schema-Version:** adr/v1

---

## Thesis

We are obsoleting human code review and enabling production-grade autonomous agentic software engineering.

Backstop is a discipline framework for AI coding agents. It ensures that code generated by agents meets enterprise-grade standards — not through human oversight, but through mechanical verification that is more rigorous, more consistent, and more trustworthy than any human reviewer.

This is the foundational bet of the entire project. Everything that follows — the artifact primitives, the validation engine, the standards packs, the provenance ledger, the verification kill chain — exists to prove this thesis mechanically. If the enforcement stack can verify every claim against every test against every standard, and the ledger can prove the work was done, and the hash chain can prove the ledger wasn't tampered with, then human review adds latency without adding safety.

**Keep reading to find out how.**

## Context

AI coding agents are shipping production code today. Copilot, Claude Code, Cursor, opencode — the tools exist and adoption is accelerating. But the industry's answer to "how do we trust agent output?" is the same answer we've had for 30 years: a human reads the diff and approves it.

This is a fundamental mismatch:

- **Agents generate code at machine speed.** Humans review at human speed. The bottleneck is now the reviewer, not the author.
- **Agents don't get tired.** Humans rubber-stamp PRs at 4pm on Friday. The reviewer is less reliable than the author.
- **Agents can be deterministic.** Given the same input and constraints, an agent can produce the same output. Humans are inconsistent across reviewers and across the same reviewer on different days.
- **Review doesn't scale.** A team shipping 50 agent-generated PRs a day cannot meaningfully review 50 PRs a day. The ceremony becomes theater.

The industry is sleepwalking into a world where agents write code and humans pretend to review it. Backstop proposes a different path: **replace the pretense with proof.**

## Decision

### Backstop is agent-first

The zeroth principle: backstop is designed for AI agents as the primary consumer, not for human developers.

After `backstop init`, the developer's role shifts from writing and reviewing code to **declaring intent and reviewing enforcement results.** The developer states what they want. The agent translates that intent into specs, plans, and code. Backstop's enforcement stack verifies the output mechanically. The developer reviews the enforcement report, not the diff.

Concretely:
- The CLI's primary consumer is agent tooling (JSON output, machine-parseable errors)
- Schemas are optimized for agent generation, not human authoring
- The validation pipeline assumes an agent is calling it, not a human typing commands
- When there's a tension between agent UX and human UX, the agent wins

This does not mean backstop is hostile to humans. Developers configure backstop, write specs, author standards. But the hot path — generate code, validate, ship — is agent-driven.

### Backstop is NOT a code quality tool

Backstop is not SonarQube. It is not ESLint. It is not a linter, a formatter, or a static analysis scanner.

Those tools answer: "Does this code follow our style guidelines?"

Backstop answers: "Was this code built according to a declared specification, verified against named test cases, by an agent whose every action is recorded in a tamper-evident ledger?"

The difference is not incremental. Code quality tools audit the artifact. Backstop audits the process that produced the artifact. A linter can tell you a function is too long. Backstop can tell you which spec requirement that function implements, which test case verifies it, whether the test body is substantive, and which agent wrote it at what time for what reason.

### The thesis restated

If the enforcement stack is collectively more rigorous than human code review — and it is, because math doesn't get tired, skip files, or rubber-stamp because it's Friday — then human review is optional. Not prohibited. Optional. Teams that want human review can have it. But backstop doesn't require it, and backstop's default is to trust the gates.

This is the single most controversial position backstop takes. It is also the single strongest differentiator. Every other tool in the market assumes a human in the loop. Backstop is designed to make that human optional.

## Consequences

### What this enables
- **Autonomous agent pipelines.** Agents generate, validate, and ship code without human intervention on the hot path.
- **Mechanical trust.** Trust is established by verification, not by a human's judgment call on a diff.
- **Speed.** Code ships at machine speed when enforcement passes. No waiting for reviewer availability.
- **Consistency.** The enforcement stack applies the same rigor to every PR, every time.

### What this requires
- **A verification stack that's actually more rigorous than human review.** This is the burden of proof backstop must meet. ADR-0008 (verification kill chain) and ADR-0009 (provenance ledger) define how.
- **Schema-driven artifacts.** Everything must be machine-parseable. No freeform docs that only humans can interpret.
- **An enforcement pipeline that cannot be bypassed.** If agents can skip validation, the thesis collapses.

### What this does NOT mean
- **Humans are banned from reviewing code.** They're welcome to. It's just not required.
- **Backstop replaces all testing.** Backstop verifies that tests exist, are named correctly, and have substantive bodies. The tests themselves still run in CI.
- **Agents are infallible.** They're not. That's why the enforcement stack exists — to catch what agents get wrong.

## Alternatives Considered

| Approach | Why Rejected |
|----------|-------------|
| Developer-first UX with agent support | Agents are already the primary code authors for early adopters. Building for humans first means retrofitting for agents later — and the retrofit never works well. |
| Code quality tooling (linting/scanning) | Audits the artifact, not the process. Cannot answer "was this built to spec?" Cannot provide provenance. Solved problem, crowded market. |
| Human-in-the-loop as hard requirement | Doesn't scale. A human reviewing 50 agent PRs/day is theater, not engineering. Baking in human review means baking in the bottleneck. |
| Advisory framework (suggestions, not enforcement) | Agents ignore suggestions. If it's not enforced, it doesn't happen. Advisory tools train humans; enforcement tools discipline agents. |
