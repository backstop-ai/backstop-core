# ADR-0014: Runtime Integration — Hooks, Runtimes, Passive Enforcement

**Number:** ADR-0014
**Created:** 2026-03-18
**Status:** Accepted
**Deciders:** @bmanson
**Decisions:** D-006, D-035, D-038, D-039, D-040, D-041, D-042
**Schema-Version:** adr/v1

---

## Context

Backstop defines standards (ADR-0006), validates them (ADR-0004), and verifies them in CI (ADR-0009). But enforcement at commit time or CI time is too late — an agent that writes 500 lines of non-compliant code before hitting a pre-commit hook wastes an entire generation cycle. The agent needs to be constrained during generation, not after.

AI agent runtimes (Copilot CLI, Claude Code, opencode, Cursor, etc.) each have their own extension points: hooks, custom agents, tool whitelists, MCP servers. Backstop must integrate with all of them without coupling to any of them. The challenge is expressing backstop's rules in a runtime-agnostic format and compiling them into runtime-specific enforcement mechanisms.

This is a Tier 4 ADR because it requires packs (ADR-0006), the validation engine (ADR-0004), and the CLI (ADR-0008) to be in place. Runtime integration is the delivery mechanism for enforcement that is defined elsewhere.

## Decision

### Compile-target model (D-006)

backstop.yml declares a list of runtimes the project targets:

```yaml
runtimes:
  - copilot-cli
  - claude-code
```

`backstop init` reads this list and generates runtime-specific configuration files and hooks. For Copilot CLI, this means generating `.github/copilot-instructions.md` and hook handlers. For Claude Code, this means generating `.claude/hooks/` scripts and `CLAUDE.md`. For other runtimes, the appropriate config artifacts are produced.

The user never sees compile-target logic. They declare runtimes; backstop handles the rest. The generated files are committed to the repository and are not hand-edited — they are compile artifacts regenerated by `backstop init`.

### Two-tier agent architecture (D-038)

Within a single runtime session, backstop supports an orchestrator agent and sub-agents. The orchestrator decomposes work (from the plan DAG) and delegates to sub-agents. Sub-agents receive tool whitelists via runtime-specific configuration (e.g., `CustomAgentConfig` in Copilot CLI).

SessionHooks fire for ALL agents in the session — orchestrator and sub-agents alike. A sub-agent with a restricted tool whitelist is still subject to the same hook-based enforcement as the orchestrator. This prevents privilege escalation through delegation.

### Agent-blind enforcement (D-039)

Hooks enforce rules based on file patterns and operation types, not agent identity. The enforcement layer does not know or care which agent is performing an operation. Two enforcement layers operate in sequence:

- **Layer 1: Capability restriction** — tool whitelists restrict which tools an agent can invoke. A sub-agent assigned to "write tests" cannot use the file-write tool on production code paths.
- **Layer 2: Compliance** — hooks inspect operation arguments against standards. A file write to `pkg/auth/` triggers the security pack's checker regardless of which agent initiated it.

This model is simpler and more secure than identity-based enforcement. There is no agent identity to spoof, no role hierarchy to maintain, and no permission matrix to misconfigure.

### Thin dispatcher hook (D-040)

The OnPreToolUse handler (or its equivalent in other runtimes) is a router, not a validator. Its logic is:

1. Extract the file path from the operation arguments.
2. Pattern-match the path against pack globs (e.g., `pkg/auth/**` → security pack).
3. Dispatch to the matching pack's checker.
4. Return the checker's verdict (allow/deny with message).

The hook file is a compile artifact generated by `backstop init`. It is not hand-authored, not hand-edited, and is regenerated whenever packs or configuration change. The dispatcher is intentionally thin — all enforcement logic lives in packs, not in the hook.

### Dispatch is a compile-target concern (D-041)

Packs declare their rules in a runtime-agnostic format: file globs, required patterns, forbidden patterns, validation functions. How those rules become executable depends on the target runtime:

- **Copilot CLI** → OnPreToolUse handler in the hooks configuration
- **Claude Code** → hooks/ shell scripts invoked by Claude's hook system
- **Other runtimes** → whatever extension mechanism the runtime provides

The compile-target abstraction means adding a new runtime requires writing a new compiler backend, not rewriting enforcement rules. Packs remain portable across all runtimes.

### Runtime integration is internal (D-042)

There is no `backstop compile` command. Compilation is an implementation detail of `backstop init`. When a user runs `backstop init`, it reads backstop.yml, resolves packs, and generates all runtime-specific artifacts. The user's mental model is: "I run init, and my runtimes are configured." The compile-target machinery is invisible.

### Pre-commit hooks largely superseded (D-035)

With runtime-level enforcement, violations are caught during generation — before a commit is even attempted. Pre-commit hooks remain only for cross-artifact, project-wide checks that cannot be expressed as per-file runtime hooks:

- Ledger hash chain integrity
- Cross-file consistency checks (e.g., spec claims vs. test names)
- Lockfile currency validation

Per-file enforcement (code style, security patterns, required sections) is handled by runtime hooks. Pre-commit is the second line of defense, not the first.

## Consequences

### What this enables
- **Enforcement during generation, not after.** Agents are constrained in real-time. A non-compliant file write is rejected before it hits disk, not caught minutes later by a linter.
- **Runtime-agnostic standards.** Teams can switch runtimes (Copilot CLI → Claude Code) without rewriting enforcement rules. Packs are portable; only the compile target changes.
- **Zero-configuration for users.** `backstop init` handles all runtime integration. Users declare runtimes in backstop.yml and never touch generated config files.
- **Sub-agent enforcement.** The two-tier architecture with session-wide hooks prevents agents from evading enforcement through delegation.

### What this requires
- **Compiler backends for each runtime.** Each supported runtime needs a backend that translates pack rules into runtime-native enforcement. This is ongoing work as new runtimes emerge.
- **Generated files must not be hand-edited.** Teams must treat runtime config files as compile artifacts. Hand-editing a generated hook file will be overwritten on the next `backstop init`.
- **Runtime hook APIs must be stable.** Backstop's compiler targets specific hook APIs. If a runtime changes its hook system, the corresponding backend must be updated.

## Alternatives Considered

| Approach | Why Rejected |
|----------|-------------|
| Runtime-specific pack definitions | Duplicates enforcement logic across runtimes. A security rule would need to be written once for Copilot, once for Claude Code, once for each new runtime. The compile-target model writes rules once. |
| MCP server for enforcement | Adds a running service dependency. Hook-based enforcement is stateless and zero-infrastructure. MCP may be useful for future features but is over-engineered for rule dispatch. |
| Pre-commit only (no runtime integration) | Too late in the pipeline. An agent that generates 500 lines of non-compliant code before hitting pre-commit wastes an entire generation cycle. Runtime enforcement catches violations immediately. |
| Manual runtime configuration | Error-prone and inconsistent. Users will misconfigure hooks, forget to update them when packs change, and diverge across team members. Generation from backstop.yml is the only reliable approach. |
