When a "consumer catalog" spec marks sites DELETED with post-cutover source "Seed N / SPEC-XXX retires it," VERIFY the named sibling spec's deletion surface actually includes that site — don't trust the catalog's self-assertion.

**Why:** SPEC-041's catalog (C-7..C-12) labels `pkg/check/check.go` passOrder + Violation.Pass/PassResult.Pass fields + Executors/applicableChecks, `manifest.go` enum+routing, `registry.go` Entries, `output.go` v.Pass rendering, `parsers.go` CheckTypeFindings as DELETED-by-SPEC-040. But verified on main + reading the sibling specs: SPEC-040 REQ-002 deletes ONLY `realCodeChecker`, `builtinToolchain` (both stacks), `resolveToolchain`/`commandExecutor` — a NARROW surface. SPEC-039 deletes only two `manifest.go` items (one routeFileDefaults branch + the compiled-standards sub-reader). NO spec deletes the `CheckType` enum, `parseCheckType`, `RouteFile`, the Pass struct fields, `output.go`, `parsers.go`, or `registry.go`'s `declaredEntries`/`defaultScopeKind`/`Entries`. So those catalog rows are mislabeled DELETED while their sites survive all sibling specs.

Two teeth: (1) false post-cutover source — the catalog asserts deletion that won't happen. (2) The catalog Site granularity is `file:symbol` ("one entry per identity-keying site") but the live `pkg/check` keying surface is much larger than the enumerated symbols — `output.go` alone has 5 `.Pass` sites (`:78/:85/:131/:135/:173`) vs catalog's one row; `check.go` has `applicableChecks` + `buildDefaultExecutors`/`...WithRunner` + two `Executors` fields; `registry.go` ~10 helper symbols. A faithful symbol-granular REQ-006 guard discovers these LIVE with no matching row → REDS ON ARRIVAL, the exact failure REQ-005 says must not happen.

**How to apply:** For catalog/inventory specs: (1) cross-check every DELETED tag against the cited deleter spec's actual deletion-surface REQ/CLM, not its summary. (2) When the spec defines Site as file:symbol and the guard scans for a token class (`.Pass`/`CheckType*`), re-grep that token class exhaustively and count DISTINCT symbols per file — coarse one-row-per-file catalogs under-enumerate and red the guard on arrival. Related: [[projectwide-locus-seam]] (the REQ-004 half of the same SPEC-041), [[existing-test-coupling]].

**Round-2 follow-up (SPEC-041 path-b correction):** the rescope to gate-semantic-only (excluding cosmetic `.Pass.String()`) is SOUND and the guard stays non-vacuous (the exclusion is display-only; scope-filter/dispatch/verdict sites stay in scope, so a real dropped gate step is still caught). The boundary is mechanically checkable (`.String()`/`%s` render = out; `==`/`map[CheckType]`/`[]CheckType{}` = in). BUT the surviving-tag direction grew its own mis-tag: SPEC-041 C-8 lists `parseCheckTypes` (plural) + "the legacy routing arm" as SURVIVING citing "SPEC-039 RETAINS" it — yet SPEC-039's CURRENT text DELETES `parseCheckTypes` and the whole `.manifest.json` routing-schema arm of LoadManifest, PRESERVING only `parseCheckType` (singular), `RouteFile`, `routeFileDefaults`, the `CheckType` enum. Lesson: when a catalog cites a sibling spec as "RETAINS X," open the sibling and match the EXACT symbol list (singular vs plural names differ) — SPEC-039 explicitly enumerates both its DELETE set and its PRESERVE set; the reviewer must diff against both, not the spec's paraphrase. Also: a "surviving" tag is only meaningful if a PRODUCTION caller remains — here `passOrder`/`Executors`/`Entries`/`buildExecutorsForConfig*` survive via the standalone `backstop code check` CLI subcommand (code_check.go, NOT the deleted gate Step 2), so the survival is real; always find the non-gate caller before accepting "surviving."
